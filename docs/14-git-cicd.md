# 14 Git・CI/CD・本番操作

[← 目次へ戻る](README.md)

## 14.1 推奨フロー

```text
エージェント
  ↓
作業ブランチ内の変更
  ↓
開発者によるdiff確認
  ↓
テスト・静的解析・シークレットスキャン
  ↓
Pull Request
  ↓
人間のレビュー・承認
  ↓
CI/CD
  ↓
環境ごとの承認ゲート
  ↓
デプロイ
```

## 14.2 エージェントへ与えない権限

[00 R2](00-red-lines.md)の具体化である。

- 保護ブランチへの直接push
- PR承認
- 本番デプロイ承認
- 本番シークレット取得
- 本番DBマイグレーション適用
- IAM・RBACの変更
- 監査ログ削除
- セキュリティ設定の無効化

## 14.3 Git運用

- エージェント作業前に作業ツリーをクリーンにする
- タスクごとにbranchまたはworktreeを分ける
- 小さい変更単位にする
- 自動生成ファイルを含めてdiffを確認
- `.git`、Hooks、CI定義、IDE・エージェント設定の変更を重点確認
- force push、history rewriteを制限
- コミット・PRのAI利用表示方針を組織で決める（コミットのtrailerやbotアカウントなど、エージェント由来の変更を後から識別できる形にする）
- エージェントに作業を依頼した人は、実質的にその変更の共同作成者である。PRのレビュー・承認は依頼者以外が行う
- エージェントの設定・指示ファイル（`AGENTS.md`・`CLAUDE.md`・`.claude/`・`.codex/`・`.mcp.json` 等）とCI定義は、CODEOWNERS等でセキュリティ担当のレビューを必須にする（[00 R6](00-red-lines.md)）
- 差分が大きいほど人間のレビューは形骸化する。1つのPRの規模に上限を設け、大きな変更は分割させる

## 14.4 CI上でエージェントを動かす場合

CI（GitHub Actions等）でエージェントを動かすと、無人実行（[4.5](04-execution-architecture.md)）に加えて、**第三者が書いた入力でジョブを起動できる**という問題が生じる。Issue本文・PRの差分・コメントはそのままエージェントへの入力になり、ジョブが持つトークンやシークレットと同じ実行環境に置かれる（[3.2](03-risks.md)の3要素がそろいやすい）。

- **起動できる人を限定する**: リポジトリへの書き込み権限を持つ利用者の操作だけを起点にする。外部コントリビューターのIssue・コメント・フォークからのPRで、シークレット付きのエージェントジョブを自動起動しない。
- **信頼できないコードとシークレットを同じジョブに置かない**: GitHub Actionsの `pull_request_target` のようにシークレットや書き込みトークンを持つトリガーで、PR側のコードをチェックアウト・実行しない。
- **Issue・PRの文字列をシェルへ直接展開しない**: タイトル・本文・ブランチ名などはワークフロー式でスクリプトへ埋め込まず、環境変数経由で渡す（コマンド注入の防止）。PR側の `AGENTS.md` 等の指示ファイルやコミットメッセージも非信頼入力である。
- **トークン権限を最小にする**: ワークフローで `permissions` を明示し、既定を読み取りにする。エージェントに必要な書き込み（作業ブランチへのpush・PR作成など）だけをジョブ単位で付与する。デプロイ用の資格情報を同じジョブに渡さない。
- **結果は作業ブランチとPRで返す**: 保護ブランチへの直接push、PRの自己承認、マージをさせない。ブランチ保護で人間のレビューを必須にする（[00 R4](00-red-lines.md)）。
- **アクションとエージェントのバージョンを固定する**: サードパーティのアクションはコミットSHAで固定し、エージェントのバージョンも固定して更新時に再テストする（[17.2](17-periodic-review.md)）。
- **ログの公開範囲を確認する**: エージェントの出力はCIログに残る。公開リポジトリではログも公開され得るため、マスキングと出力内容を確認する。
- **ランナーを使い捨てにする**: 永続的なセルフホストランナーは、前のジョブの状態や資格情報を次のジョブへ残し得る。エフェメラルなランナーを使う。

製品別の実装例: Anthropic の `claude-code-action`、OpenAI の `codex-action` は、いずれも既定でリポジトリへの書き込み権限を持つ利用者だけが起動できる。書き込み権限のない利用者や bot へ広げる設定（`allowed_non_write_users`・`allowed_bots`、`allow-users`・`allow-bots` 等）は、公式にも危険と明記されている。採用する場合は、権限を極小にしたワークフローに限る（[20](20-references.md)）。

> [!NOTE]
> 2025-08 の Nx「s1ngularity」事件は、PRタイトル経由のコマンド注入が可能な `pull_request_target` ワークフローから npm 公開トークンが盗まれたことが発端だった（[3.1](03-risks.md)）。CIのトリガーと権限の設計は、エージェントを動かすかどうかにかかわらず、ここで挙げた観点で見直す。
