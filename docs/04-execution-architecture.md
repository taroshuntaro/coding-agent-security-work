# 04 IDE・エディタに依存しない実行構成

[← 目次へ戻る](README.md)

## 4.1 推奨構成A: エディタが開発コンテナへ接続する

```text
ホストOS
├─ エディタのUI
├─ コンテナランタイム
└─ 開発コンテナ
   ├─ コーディングエージェント（Codex・Claude Code 等）
   ├─ Git
   ├─ 言語ランタイム・SDK
   ├─ Lint・テスト・ビルドツール
   └─ プロジェクト
```

エディタがDev Container仕様やリモート開発に対応している場合に適する。エディタの画面はホストで動作するが、ターミナル、エージェント、ビルド、テストはコンテナ内で実行する。

## 4.2 推奨構成B: エディタはホスト、エージェントだけコンテナで実行する

```text
ホストOS
├─ 任意のエディタ
├─ project/  ───── bind mount ────┐
└─ コンテナランタイム             │
                                  ▼
                           開発コンテナ
                           ├─ /workspace/project
                           └─ コーディングエージェント
```

IDEがコンテナ接続に対応していなくても採用できる。ホストのエディタで編集し、エージェントは `docker exec`、Compose、専用ランチャーなどからコンテナ内で起動する。

注意点:

- プロジェクトは複製されず、通常は同じホストファイルを参照する。
- コンテナ内の変更は、ホスト上のプロジェクトへ直接反映される。
- ホスト側IDEが実行するビルド、拡張機能、言語サーバーはコンテナ境界の外にある。
- エージェントの影響範囲は限定できるが、プロジェクト内のファイル破壊までは防げない。

## 4.3 推奨構成C: 専用VM・クラウド開発環境へリモート接続する

```text
開発者端末
└─ エディタ / SSH / Remote Development
   ↓
専用VM・VDI・クラウド開発環境
└─ コンテナまたは直接実行
   ├─ コーディングエージェント（Codex・Claude Code 等）
   └─ プロジェクト
```

顧客機密や高機密案件に適する。ソースコードやシークレットを開発者端末へ残さず、接続先を集中管理できる。

## 4.4 ベンダーのクラウド環境で動くエージェント

```text
開発者（Web・IDE・チャット・Issueから依頼）
   ↓
ベンダー管理のクラウド環境（タスクごとのコンテナ・VM）
   ├─ コーディングエージェント
   └─ リポジトリのクローン
   ↓
ブランチ・Pull Request として結果を返す
```

Codex web、Claude Code on the web、GitHub Copilot coding agent、Cursor background agents など、エージェントをベンダーのクラウド環境で動かす形態である。ローカル端末とは分離されるため、ホストの資格情報やホームディレクトリへは到達しない。一方で、次を別途審査する。

- **データの所在**: リポジトリ・会話・ログ・環境キャッシュがベンダー側に保存される。契約・データ保持・リージョンを確認する（[00 R1](00-red-lines.md)）。
- **リポジトリ接続の権限**: GitHub App 等で付与するリポジトリの範囲と書き込み権限を最小にする。
- **環境のネットワーク**: エージェント実行中のインターネットアクセスは原則無効、必要時は許可ドメインを限定する。
- **環境に渡すシークレット**: セットアップ時だけ必要な値と、エージェント実行中も見える値を区別する。
- **依頼できる人**: Issueの割り当てやチャットからタスクを起動できる場合、誰の依頼でどの権限で動くかを確認する。第三者が書いたIssue本文は非信頼入力である（[3.2](03-risks.md)）。
- **結果の統合**: 結果はPRとして受け取り、人間がレビューしてから統合する（[00 R4](00-red-lines.md)）。

製品別の設定は[10.6](10-codex.md)（Codex web）・[11.11](11-claude-code.md)（Claude Codeのバックグラウンドエージェント・Remote Control）を参照する。

## 4.5 CI・スケジュール実行など無人で動くエージェント

エージェントをCI（GitHub Actions等）、定期ジョブ、ヘッドレスモードで実行する形態である。**実行中に承認する人間がいない**ため、承認プロンプトに頼った統制はすべて効かない。

- 承認に頼っていた操作は、deny・サンドボックス・トークン権限・ネットワーク制限で到達不能にするか、作業範囲から外す。
- 使い捨ての実行環境（エフェメラルなランナー・コンテナ）で動かし、ジョブ間で状態を残さない。
- 起動のきっかけ（Issue・PRコメント等）と、ジョブに渡す資格情報の組み合わせに注意する。詳細は[14.4](14-git-cicd.md)。

## 4.6 リポジトリが定義する開発環境を自動的に信頼しない

次のファイルは、コンテナを利用するための設定である一方、ビルド時・起動時・接続時にコードを実行できる（[00 R6](00-red-lines.md)）。

- `.devcontainer/devcontainer.json`
- `Dockerfile`、Composeファイル
- `postCreateCommand`、`postStartCommand`などのライフサイクルコマンド
- Maven/Gradle/npmなどのプラグイン・lifecycle script
- Git Hooks、Claude Code Hooks、Codex Hooks
- `.mcp.json`、エージェント設定、プロジェクト指示ファイル

初回チェックアウト直後に自動ビルド・自動接続せず、内容をレビューする。特に、Dockerソケット、ホストディレクトリ、SSH Agent、クラウド資格情報、デバイスをマウントする定義を要審査とする。

コンテナ内でエージェントを動かしても、**コンテナを作成する処理自体**がホストのDocker Engineやビルド機構で動く点に注意する。

## 4.7 Windows環境の考え方

製品組み込みサンドボックスの対応範囲はOSごとに異なる。特にClaude CodeのBash sandboxはmacOS、Linux、WSL2が対象であり、Windowsネイティブ環境とWSL1を同等に扱わない。

Windows中心の開発では、次のいずれかを標準化すると管理しやすい。

- WSL2内でエージェントを実行する
- Docker Desktop等のLinuxコンテナ内で実行する
- 専用Linux VM・クラウド開発環境へ接続する

Codexについても、ネイティブWindows、WSL、コンテナで実装・制約が異なるため、対象OSごとにポリシーテストを行う。
